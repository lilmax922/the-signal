## Open Questions

- **Slug uniqueness retry**: The current `refinery-agent.ts` calls `insertSignal` with the base `generateSlug(...)` output. If two articles happen to produce the same `{slugified-title-en}-{YYYYMMDD}` on the same day, the second insert will hit the `slug` unique constraint and bubble up as a task failure (Trigger.dev retries, but the retry is likely to hit the same conflict). Architecture.md mandates `-2` / `-3` / … / `-10` retry-with-suffix. Defer to a follow-up feature unit — no production impact right now (the rss-ingestion dedup by `guid` already covers the common case).
- **Postgres advisory lock or named constraint for the refinery transaction**: Currently `refinery-agent.ts` runs `db.transaction(...)` inside the Trigger.dev worker. Trigger.dev already provides run-level isolation via `ctx.run.id`, but two concurrent runs that happen to share a `guid` (very unlikely given the rss-ingestion dedup, but possible during a manual re-trigger) could in theory race. The `guid` unique constraint makes the loser fail safely. No action needed.

## Architecture Decisions

- **ESLint Configuration Strategy**: Use separate config objects in the flat config array to target specific file types for rules that rely on specific parsers (e.g., Vue rules). This prevents crashes when linting non-target files like Markdown.
- **Design System Configuration**: Use `app.config.ts` for color palette selection (`primary: 'brand'`, `neutral: 'neutral'`) and CSS `@theme static` block for custom color definitions with OKLCH values.
- **Layout Component Strategy**: Desktop shows header with search and avatar dropdown; mobile header collapses on scroll with hysteresis threshold, shows search bar and category filter below title.
- **Scroll Collapse Pattern**: Created generic `useScrollCollapse` composable and `AppScrollCollapseSection` wrapper component to handle scroll-based show/hide behavior. This keeps scroll logic encapsulated and reusable. CategoryFilter remains a pure presentational component without scroll awareness.
- **Objective Minimalist Typography System**: Configured a clinical, language-agnostic typography system in `ui-context.md` pairing standard readable sans-serif fonts with a monospace stack (`JetBrains Mono` / `Fira Code`). The system uses the standard Tailwind CSS size scale (`text-xs` to `text-2xl`), restricts weights to a maximum of `600` (Semi-Bold), and forbids bold text and italics in de-noised content to preserve neutrality. Enforces tabular figures (`tabular-nums`) for column alignment and specifies background-color-free entity tags for clean typography.
- **Trigger.dev Configuration**: Uses `trigger.config.ts` with `dirs: ["./trigger"]`, node-22 runtime, and retries disabled in development. Tasks are schemaTask with Zod validation for type-safe payloads. The Nitro RSS ingestion task acts as the orchestrator, triggering the Trigger.dev refinery pipeline for article processing.
- **Transactional DB Writes in the Pipeline**: All three persistence steps (insertSignal → insertTag → insertSignalTag) run inside a single `db.transaction(async (tx) => …)` inside `refinery-agent.ts`. Helpers accept an optional `DbClient` (`typeof db | transaction client`) so they remain composable. Each helper validates the incoming payload with `InsertXxxSchema.safeParse(...)` (throwing on failure) and replaces the previous `!` non-null assertion on the `.returning()` row with an explicit `if (!inserted) throw` check. Returning the inserted rows from the transaction gives the caller full IDs in one round-trip and surfaces any failure to the Trigger.dev retry path.
- **Tag Insert (Internally Upsert)**: The `insertTag` helper calls `onConflictDoUpdate({ target: tag.name, set: { name: sql\`excluded.name\` } })` internally. The `set` clause is a no-op (assigning `name` to its own value), and Drizzle's `$onUpdate(() => new Date())` callback does not fire on the `onConflictDoUpdate` path — so `updated_at` is never touched spuriously, and `.returning()` always yields the row (no `findTagByName` fallback needed). The function is named `insertTag` for consistency with the other insert helpers; the upsert nature is an internal implementation detail.
- **Insert Schemas Co-located with Drizzle Tables**: `drizzle-zod`'s `createInsertSchema(table).omit(...)` derives the insertable shape from the same source of truth as the table definition, so column name casing and nullability stay in lock-step. The schemas live in the same files as the table definitions (`server/database/schema/{signal,tag,signal-tag}.ts`) rather than a separate `schemas/` directory — matches `architecture.md` and `code-standards.md`, both of which prescribe a singular `schema/`.
- **Refinery Pipeline Log Vocabulary**: `trigger/refinery-agent.ts` uses a single `LOG` constants object (`refinery.start`, `refinery.extract.ok`, `refinery.refine.ok`, `refinery.slug.ok`, `refinery.mirror.{ok,skipped,err}`, `refinery.persist.ok`, `refinery.complete`) — every `logger.*` call passes a stable key as the message and dynamic data as a structured `properties` object. No string interpolation in messages, no embedding of `guid`/`pipelineRunId` in message text. The same `log(stage)` arrow spreads `{ pipelineRunId, guid, stage }` into every call so the three context fields appear on every line of the run's log timeline (and are filterable in the Trigger.dev dashboard). Failures throw `RefineryError` with a typed `code` from a fixed union — the dashboard error panel groups runs by code instead of by raw stack trace. The 5 stages stay as commented step blocks in a single linear `run()` body (no helper functions, no file split); the linear shape is preferred over decomposition because the function is the orchestrator, not a library, and a reader can scan the full pipeline top-to-bottom in one screen.
- **Cursor Index Design (`id` not `slug` as tiebreaker)**: The cursor encodes `base64({publishedAt-iso}|{id-uuid})` — `id` is the tiebreaker column in the composite index, not `slug`. Three reasons: (1) `id` is a fixed-size 16-byte UUID; `slug` is variable-length text (30–60 bytes) — smaller key columns mean a shallower B-tree and more entries per leaf page. (2) `id` is immutable; `slug` is theoretically mutable (a rename would invalidate every outstanding cursor pointing to that row). (3) `id` is the canonical internal handle; `slug` is the public URL identifier. The two identifier systems serve different audiences (machine-internal vs. human-shareable) and the cursor belongs to the internal one. Postgres B-tree's **leftmost prefix rule** means the composite `(published_at DESC, id DESC)` also serves any `ORDER BY published_at` query, which is why the legacy single-column `idx_signal_published_at` is dropped — keeping it would duplicate write overhead for zero query benefit.
- **Feed schema derived from full signal schema (no field duplication)**: `signalFeedSchema` is `signalSchema.omit({ contentEn, contentZh, summaryEn, sourceUrl })` — the field set is defined exactly once in `signalSchema`, and the lightweight feed card picks it up automatically. Adding a new field to `signalSchema` (e.g. `readingTimeMinutes`) flows through to the feed shape unless explicitly omitted; reviewers only need to audit the `omit` list when fields change. The 3-item `summaryEn` / `summaryZh` refinement is also shared as a small `summarySchema` helper inside `shared/validators/signal.ts` (used by `signalSchema`; `InsertSignal` in `server/database/schema/signal.ts` still applies the same refinement at the persistence layer via its own callback — that duplication is one line each and keeps the insert / response paths independent).
- **Cross-boundary alias bridging (Nuxt `#shared` → Trigger.dev esbuild)**: Nuxt's `#shared` alias is generated at Nuxt build time into `.nuxt/tsconfig.server.json` and is invisible to the trigger.dev CLI's esbuild bundler — so `server/database/queries/signal.ts:7` (and any other server file using `#shared/...`) fails to resolve when the trigger build follows the import chain. Considered and rejected options: (a) using the trigger config's `tsconfig` option — the schema accepts it but the bundler code in `@trigger.dev/core/dist/esm/v3/build/bundle.js:97` doesn't pass it through to esbuild, so it has no effect on module resolution (it's only used to read the file's source for indexing in `sourceFiles.js:17`); (b) installing `tsconfig-paths/register` at the top of `trigger.config.ts` — only affects the config file's own resolution, not the bundled output; (c) rewriting the offending server files to use relative paths — works but breaks the `#shared` consistency between Nitro and trigger. Chosen: a small custom esbuild plugin registered through the `build.extensions` API in `trigger.config.ts` (the `nuxt-alias-resolver` extension, ~15 lines). It registers an esbuild `onResolve` handler that matches `^#shared(?:/|$)` and returns the absolute `<root>/shared[/...].ts` path; the `.ts` suffix is appended directly because the `shared/` tree is TypeScript-only (verified — 7 files, all `.ts`). The extension lives in `trigger.config.ts` next to the `defineConfig` call so the trigger build and the alias mirror are in the same place; the comment in `trigger.config.ts` documents the mirror-with-`nuxt.config.ts` invariant. Any new `#`-prefixed alias added to `nuxt.config.ts` (e.g. `#server`) must be mirrored here — this is a known follow-up risk and is captured in the `architecture.md` stack table as a "Cross-boundary alias bridging" note.

- **Drizzle enum diff side-effect of module-private `categoryEnum`**: Because spec #10 made `categoryEnum` a module-private constant (not re-exported from `server/database/schema/index.ts`), Drizzle's snapshot diff never sees the enum in the schema namespace — the snapshot's `enums` field stays `{}` instead of `{ "public.category": { … } }`. This breaks generated migrations in **both directions**:
  - **Incremental migration on an existing DB**: Drizzle sees the enum in the old snapshot but not the new one, so it emits a spurious `DROP TYPE "public"."category"` line at the end of the migration. The `signal.category` column still depends on the type — leaving the line in would fail the migration or destroy the type and break all rows. **Fix**: manually strip the `DROP TYPE` line before running `pnpm db:migrate`.
  - **Fresh migration on an empty DB**: Drizzle never sees the enum, so it skips the `CREATE TYPE "public.category" AS ENUM('finance', 'tech', 'world')` line entirely. The first `CREATE TABLE signal` would then fail with `type "category" does not exist`. **Fix**: manually prepend the `CREATE TYPE` line to the migration before running `pnpm db:migrate`.
  - This is a known trade-off of the spec #10 design decision (the module-private refactor is required to satisfy `PostgresJsTransaction`'s `TablesRelationalConfig` constraint). Document the fix in code review and add it to the migration checklist going forward. A future refactor could move `categoryEnum` to a dedicated `server/database/schema/enums.ts` file and re-export it from `schema/index.ts` — Drizzle's namespace scan would then pick it up automatically and the manual fix disappears, at the cost of the relational-config constraint needing a different workaround.
